## 2. Restore SQL Safety & `session_replication_role` Audit

### Technical Review of `SET session_replication_role = replica`
In earlier iterations of database backup workflows, `SET session_replication_role = replica;` was frequently used to disable trigger loops and bypass foreign-key checking during bulk insertion. However, a rigorous security and stability audit reveals why this practice must **NOT** be used in Aurelia's production disaster-recovery pipeline:

1. **Permission Constraints in Managed PostgreSQL**:
   - Setting `session_replication_role` in PostgreSQL requires superuser privileges (`superuser`).
   - In Supabase and modern managed cloud PostgreSQL providers, application connection poolers (PgBouncer/Supavisor), restricted roles, and developer credentials do not possess superuser privileges. Running this statement under standard connection pools fails with permission denied errors.
2. **Harmful Trigger Suppression**:
   - `session_replication_role = replica` suppresses **ALL** standard user-defined triggers, including:
     - `update_updated_at_column()`: Prevents timestamps from tracking updates accurately.
     - `on_auth_user_created`: Bypasses default profile generation.
     - Custom audit and rate-limit triggers.
3. **Suppression of Referential Integrity Validation**:
   - In `replica` mode, PostgreSQL disables foreign-key constraint enforcement. If any corrupted or orphaned records exist in a backup, they are inserted silently without validation.
   - If a script execution errors out mid-way while in `replica` mode, the connection remains in replica mode, silently compromising constraint checks for all subsequent queries in that session.

### Hardened Architecture: Dependency-Ordered & Idempotent Insertion
To ensure safe, robust restoration under standard database privileges without bypassing PostgreSQL constraints or triggers:
1. **Topological Foreign-Key Dependency Ordering**: Records are inserted in strict hierarchical levels (Level 1 Root Entities $\rightarrow$ Level 2 Core Entities $\rightarrow$ Level 3 Junctions $\rightarrow$ Level 4 Grandchildren).
2. **Idempotent Conflict Handling**: Every INSERT statement generates an `ON CONFLICT (...) DO UPDATE SET ...` clause for entity tables, and `ON CONFLICT (...) DO NOTHING` for junction tables. This allows safe, repeatable restoration without primary-key collisions.
3. **Generated Column Exclusion**: PostgreSQL `GENERATED ALWAYS AS (...) STORED` columns (specifically `recipes.fts`) are automatically filtered out from the INSERT column list, allowing PostgreSQL to calculate search vectors natively on row insertion.
4. **Trigger Compatibility**: When `auth/auth-recovery.sql` creates users in `auth.users`, Supabase's `on_auth_user_created` trigger auto-creates a default row in `public.profiles`. When `data/restore-data.sql` then inserts into `public.profiles`, its `ON CONFLICT (id) DO UPDATE SET` cleanly merges the user's backed-up profile data without failing on duplicate key constraints.

## 6. Pre-Provisioning Auth User UUIDs (Step 3)

### The Foreign-Key Anchor Dilemma
Every user-owned table (`profiles`, `recipes`, `collections`, `shopping_lists`, `tags`, etc.) enforces `REFERENCES auth.users(id) ON DELETE CASCADE`. In a newly provisioned Supabase project, `auth.users` is completely empty. Attempting to insert into `public.recipes` or `public.profiles` before `auth.users` contains records will immediately fail with foreign-key constraint violations!

### Recovery Procedure:
1. In the target Supabase Dashboard **SQL Editor**, open `auth/auth-recovery.sql` from the backup archive.
2. Click **Run**.
3. This creates anchor rows in `auth.users` with the exact original user UUIDs, verified email addresses, and metadata, with blank password hashes.
4. The database trigger `on_auth_user_created` will fire and create stub rows in `public.profiles`.

### What Can vs Cannot Be Restored:
| Capability | Status | Details |
| :--- | :---: | :--- |
| **User UUIDs** | **Preserved 100%** | Exact original UUIDs are restored, satisfying all child foreign keys. |
| **Email & Metadata** | **Preserved 100%** | User email, display name, avatar URL, and app metadata are restored. |
| **Profile & Data Ownership**| **Preserved 100%** | Recipes, collections, favorites, and meal plans remain linked to their owners. |
| **Password Hashes** | **Not Exported** | Excluded for security. Users establish new passwords via password reset. |
| **Active Sessions & Tokens**| **Revoked** | All sessions terminate; users authenticate cleanly on the new project. |
| **MFA TOTP Factors** | **Re-enrolled** | Users must re-configure 2FA authenticators upon logging in. |

### How Users Regain Access:
1. **Google OAuth Users**:
   - When Google OAuth is enabled in the new project with the Google Client ID & Secret, Gotrue automatically matches the user by their verified email address upon their first sign-in.
   - The user is signed in with their restored UUID and immediately sees all their recipes and data.
2. **Email/Password Users**:
   - Because password hashes are not exported, users cannot log in with their old password.

   - **Admin-Triggered**: In Supabase Dashboard -> **Authentication -> Users**, click `...` next to any user and select **Send Password Reset**, or execute:
     ```typescript

     ```

## 9. Backup Archive Protection, Safe Decryption & Credential Security

To safeguard user data in transit or off-site, the backup tools provide multiple input modes that guarantee passphrases are never logged, echoed in terminals, or saved to shell history:

### Passphrase Resolution Hierarchy:
1. **Windows Credential Manager Target (`--cred-target <target>` or Automatic Archive Lookup)**:
   - Queries Windows Credential Manager via native Win32 `advapi32::CredReadW` API without exposing secrets in process command-line arguments.
   - Automatically attempts to load target `AureliaBackup_<timestamp>` matching the backup archive.
2. **DPAPI-Protected Key File (`--dpapi-file <path>` or `.key.dpapi`)**:
   - Decrypts key material encrypted at rest via Windows Data Protection API (`[System.Security.Cryptography.ProtectedData]` under `CurrentUser` scope).
   - Only processes running in the current logged-in Windows user session can decrypt the key file.
3. **Interactive Masked Prompt** (Default in TTY): Terminal input is suppressed (`*` masking).
4. **Standard Input Pipe (`--stdin`)**: Allows piping securely from external password managers (e.g. Bitwarden, 1Password CLI):
   ```powershell
   bws secret get <secret-id> | npx tsx scripts/backup/decrypt-backup.ts --stdin --file "C:\AureliaBackups\backup.enc"
   ```
5. **Password File (`--password-file <path>`)**: Reads from a secure local credential file (auto-detecting DPAPI if `.dpapi`).
6. **Environment Variable (`AURELIA_BACKUP_PASSPHRASE`)**: Injected into process memory.

### Plaintext Key Migration & Storage Exposure
During the security audit, `C:\Users\svish\AureliaBackups\2026-10-25_14-50-25.key` was inspected and found to contain the 256-bit passphrase in plaintext. 
- **The Exposure**: Storing a plaintext decryption passphrase on the same storage filesystem right next to the `.enc` container negates the benefit of AES-256 encryption at rest if the drive or directory is exfiltrated or copied.
- **Migration Performed**:
  1. The passphrase was securely migrated into **Windows Credential Manager** under generic credential target `AureliaBackup_2026-10-25_14-50-25`.
  2. A secondary DPAPI-encrypted container was generated at `C:\Users\svish\AureliaBackups\2026-10-25_14-50-25.key.dpapi`.
  3. Decryption was tested and verified end-to-end using Windows Credential Manager, DPAPI, and standard input piping (`--stdin`).
  4. The plaintext `.key` file was removed via Windows PowerShell `Remove-Item`. Note: On standard NTFS filesystems, `Remove-Item` unlinks the directory entry from the Master File Table (MFT); it does **not** perform a cryptographic wipe or multi-pass disk shredding. The exposure risk going forward is eliminated because the backup tooling no longer writes plaintext `.key` files.

### Cross-Device Passphrase Storage & Disaster Recovery
Because Windows Credential Manager and DPAPI are cryptographically bound to the local Windows user profile and machine SID, losing this laptop or reinstalling Windows would prevent decryption if no external copy exists. To ensure true disaster recovery across any device without ever printing or logging the secret:

#### Step 1: Securely Copy Passphrase to System Clipboard (Zero Console Echo)
Run the built-in clipboard copy action. This reads from Windows Credential Manager and injects the passphrase directly into the Windows clipboard in memory, without printing, logging, or writing to disk:
```powershell
powershell -ExecutionPolicy Bypass -File scripts\backup\win-cred.ps1 -Action CopyToClipboard -Target "AureliaBackup_2026-10-25_14-50-25"
```

#### Step 2: Store in a Cloud-Synced Password Manager
1. Open your cross-device password manager (e.g. **Bitwarden**, **1Password**, **KeePassXC**, **Apple Keychain**, or **Proton Pass**) on this PC or linked mobile phone.
2. Create a new entry:
   - **Title**: `Aurelia Backup Passphrase - 2026-10-25_14-50-25`
   - **Category**: Secure Note or Password
   - **Secret Field**: Paste (`Ctrl+V`) directly from clipboard.
3. Save and sync across devices.
4. Immediately clear your clipboard:
   ```powershell
   Clear-Clipboard
   ```

#### Step 3: Decrypting on a Completely Different Machine (Lost Laptop Scenario)
If this workstation is lost or destroyed, you can restore from any Mac, Linux, or Windows machine:
1. Copy the encrypted archive (`2026-10-25_14-50-25.enc`) from off-site storage.
2. Clone the repository and install Node.js dependencies (`npm install`).
3. Run the decryption command:
   ```bash
   npx tsx scripts/backup/decrypt-backup.ts --file 2026-10-25_14-50-25.enc
   ```
4. When prompted (`Enter backup passphrase to decrypt: `), copy the passphrase from your password manager app on your phone and paste it directly into the masked prompt, or pipe it securely:
   ```bash
   # Or via standard input on any platform:
   cat secret.txt | npx tsx scripts/backup/decrypt-backup.ts --file 2026-10-25_14-50-25.enc --stdin
   ```
   *Note*: The CLI automatically strips leading UTF-8 Byte Order Marks (`\uFEFF`) and trailing newlines, ensuring 100% cross-platform compatibility.

1. **Supabase GoTrue Auth Daemon**: PGlite executes PostgreSQL SQL statements; it does not run the Supabase GoTrue Go daemon. The test does not verify GoTrue's HTTP endpoints, JWT signing, refresh token rotation, or session persistence.
2. **Live Google OAuth Exchange**: The test does not perform real browser redirects, PKCE code exchange, or live Google OAuth 2.0 handshake. Automatic account linking for OAuth users is an architectural capability of GoTrue, not a verified end-to-end test result.
3. **Password-Reset Email Delivery**: The test does not test SMTP mail transport, rate-limiting, or whether Supabase's email service successfully delivers password recovery emails to users.
4. **PostgREST HTTP / Realtime Replication**: The test does not verify PostgREST REST API serialization, schema reloading (`NOTIFY pgrst, 'reload schema'`), or Realtime WebSocket replication.
5. **Supabase Storage S3/TUS Endpoints**: While the test verifies that 6 image binary files exist on disk with matching SHA-256 hashes (1.42 MB) and tests bucket table schema creation, it does not perform live network HTTP multipart uploads over Supabase Storage S3/TUS endpoints.
