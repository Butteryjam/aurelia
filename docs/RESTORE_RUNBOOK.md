# Aurelia Disaster Recovery & Restore Runbook

> **CRITICAL OPERATIONAL SAFETY RULE**  
> **NEVER run a restore against the production project (`upzkcqovqstfsizerulx`)!**  
> Do not execute destructive SQL, reset the production database, delete remote files, or overwrite real user data.  
> This runbook is intended solely for recovering to a clean, newly provisioned disaster-recovery project or isolated staging environment.

## 1. Overview & Recovery Objectives

This runbook outlines the hardened, step-by-step procedure to restore Aurelia's database schema, application records, recipe photography, and service configuration from a verified backup archive generated by `scripts/backup/backup.ts`.

### Backup Archive Directory Structure
Each backup is timestamped and saved outside the repository at `%USERPROFILE%\AureliaBackups\<TIMESTAMP>\`:

```text
%USERPROFILE%\AureliaBackups\<TIMESTAMP>\
  ├── manifest.json                    # Cryptographic SHA-256 manifest & table inventory
  ├── schema/
  │   ├── consolidated_schema.sql      # Complete unified schema (DDL, RLS, functions, triggers)
  │   └── migrations/                  # Full sequence of Supabase migrations (00001 to 00006)
  ├── data/
  │   ├── restore-data.sql             # Dependency-ordered SQL INSERT script (with ON CONFLICT handling)
  │   ├── remap-storage-urls.sql       # Automated SQL helper to remap image URLs to the new project
  │   └── <table_name>.json            # Individual JSON data dumps for each of the 21 tables
  ├── storage/
  │   ├── storage-inventory.json       # Inventory of image files, sizes, MIME types, and hashes
  │   └── recipe-images/               # Downloaded recipe photography files
  │       └── <user_id>/<file_name>
  ├── auth/
  │   ├── users-inventory.json         # Safe user metadata (strictly excluding password hashes)
  │   └── auth-recovery.sql            # Pre-provisioning SQL anchors for user UUID preservation
  └── config/
      └── disaster-recovery-config.json # Required environment variables and dashboard settings
```

## 2. Restore SQL Safety & `session_replication_role` Audit

### Technical Review of `SET session_replication_role = replica`
In earlier iterations of database backup workflows, `SET session_replication_role = replica;` was frequently used to disable trigger loops and bypass foreign-key checking during bulk insertion. However, a rigorous security and stability audit reveals why this practice must **NOT** be used in Aurelia's production disaster-recovery pipeline:

1. **Permission Constraints in Managed PostgreSQL**:
   - Setting `session_replication_role` in PostgreSQL requires superuser privileges (`superuser`).
   - In Supabase and modern managed cloud PostgreSQL providers, application connection poolers (PgBouncer/Supavisor), restricted roles, and developer credentials do not possess superuser privileges. Running this statement under standard connection pools fails with permission denied errors.
2. **Harmful Trigger Suppression**:
   - `session_replication_role = replica` suppresses **ALL** standard user-defined triggers, including:
     - `update_updated_at_column()`: Prevents timestamps from tracking updates accurately.
     - `on_auth_user_created`: Bypasses default profile generation.
     - Custom audit and rate-limit triggers.
3. **Suppression of Referential Integrity Validation**:
   - In `replica` mode, PostgreSQL disables foreign-key constraint enforcement. If any corrupted or orphaned records exist in a backup, they are inserted silently without validation.
   - If a script execution errors out mid-way while in `replica` mode, the connection remains in replica mode, silently compromising constraint checks for all subsequent queries in that session.

### Hardened Architecture: Dependency-Ordered & Idempotent Insertion
To ensure safe, robust restoration under standard database privileges without bypassing PostgreSQL constraints or triggers:
1. **Topological Foreign-Key Dependency Ordering**: Records are inserted in strict hierarchical levels (Level 1 Root Entities $\rightarrow$ Level 2 Core Entities $\rightarrow$ Level 3 Junctions $\rightarrow$ Level 4 Grandchildren).
2. **Idempotent Conflict Handling**: Every INSERT statement generates an `ON CONFLICT (...) DO UPDATE SET ...` clause for entity tables, and `ON CONFLICT (...) DO NOTHING` for junction tables. This allows safe, repeatable restoration without primary-key collisions.
3. **Generated Column Exclusion**: PostgreSQL `GENERATED ALWAYS AS (...) STORED` columns (specifically `recipes.fts`) are automatically filtered out from the INSERT column list, allowing PostgreSQL to calculate search vectors natively on row insertion.
4. **Trigger Compatibility**: When `auth/auth-recovery.sql` creates users in `auth.users`, Supabase's `on_auth_user_created` trigger auto-creates a default row in `public.profiles`. When `data/restore-data.sql` then inserts into `public.profiles`, its `ON CONFLICT (id) DO UPDATE SET` cleanly merges the user's backed-up profile data without failing on duplicate key constraints.

## 3. Pre-Flight Verification (Step 0)

Before initiating recovery, cryptographically verify the integrity of the backup archive to guarantee no files are missing or corrupted:

```powershell
# From the repository root (C:\RecipeVault  mobile version):
npx tsx scripts/backup/verify-backup.ts --dir "C:\Users\<username>\AureliaBackups\<TIMESTAMP>"
```

### The 7-Step Verification Suite Checks:
1. `manifest.json` existence and JSON schema validity.
2. Cryptographic SHA-256 hashes of every backed-up file against recorded hashes.
3. Table row counts for all 21 application tables match recorded inventory.
4. Storage image objects exist on disk, match recorded sizes, and pass SHA-256 verification.
5. Auth inventory strictly adheres to zero-credential privacy rules (no passwords or tokens).
6. Cross-verifies all database `image_url` and `cover_image_url` references against storage files.
7. Cross-verifies all record ownership foreign keys against valid user anchors in auth inventory.

If any checksum fails or files are missing, do not proceed with that archive; use the previous verified backup run.

## 6. Pre-Provisioning Auth User UUIDs (Step 3)

### The Foreign-Key Anchor Dilemma
Every user-owned table (`profiles`, `recipes`, `collections`, `shopping_lists`, `tags`, etc.) enforces `REFERENCES auth.users(id) ON DELETE CASCADE`. In a newly provisioned Supabase project, `auth.users` is completely empty. Attempting to insert into `public.recipes` or `public.profiles` before `auth.users` contains records will immediately fail with foreign-key constraint violations!

### Recovery Procedure:
1. In the target Supabase Dashboard **SQL Editor**, open `auth/auth-recovery.sql` from the backup archive.
2. Click **Run**.
3. This creates anchor rows in `auth.users` with the exact original user UUIDs, verified email addresses, and metadata, with blank password hashes.
4. The database trigger `on_auth_user_created` will fire and create stub rows in `public.profiles`.

### What Can vs Cannot Be Restored:
| Capability | Status | Details |
| :--- | :---: | :--- |
| **User UUIDs** | **Preserved 100%** | Exact original UUIDs are restored, satisfying all child foreign keys. |
| **Email & Metadata** | **Preserved 100%** | User email, display name, avatar URL, and app metadata are restored. |
| **Profile & Data Ownership**| **Preserved 100%** | Recipes, collections, favorites, and meal plans remain linked to their owners. |
| **Password Hashes** | **Not Exported** | Excluded for security. Users establish new passwords via password reset. |
| **Active Sessions & Tokens**| **Revoked** | All sessions terminate; users authenticate cleanly on the new project. |
| **MFA TOTP Factors** | **Re-enrolled** | Users must re-configure 2FA authenticators upon logging in. |

### How Users Regain Access:
1. **Google OAuth Users**:
   - When Google OAuth is enabled in the new project with the Google Client ID & Secret, Gotrue automatically matches the user by their verified email address upon their first sign-in.
   - The user is signed in with their restored UUID and immediately sees all their recipes and data.
2. **Email/Password Users**:
   - Because password hashes are not exported, users cannot log in with their old password.
   - **Self-Service**: The user clicks **Forgot Password** on `/auth/login`, receives a secure password reset email from Supabase, sets their new password, and logs in.
   - **Admin-Triggered**: In Supabase Dashboard -> **Authentication -> Users**, click `...` next to any user and select **Send Password Reset**, or execute:
     ```typescript
     await supabase.auth.admin.generateLink({ type: 'recovery', email: user.email })
     ```

### Row Count Verification Query:
Run the following SQL in the target project to verify row counts match the backup manifest:

```sql
SELECT 
  table_name,
  (xpath('/row/c/text()', query_to_xml(format('select count(*) as c from %I.%I', table_schema, table_name), false, true, '')))[1]::text::int AS row_count
FROM information_schema.tables 
WHERE table_schema = 'public' AND table_type = 'BASE TABLE'
ORDER BY table_name;
```

## 8. Restoring Recipe Photography & Remapping URLs (Step 5)

Database records reference image URLs under the `recipe-images` bucket. The bucket was created by `schema/consolidated_schema.sql` (Migration 00002).

### Automated Storage Upload:
Run the restore helper with the target project's credentials:

```powershell
$env:RESTORE_TARGET_SUPABASE_URL = "https://<new-ref>.supabase.co"
$env:RESTORE_TARGET_SERVICE_ROLE_KEY = "<new-service-role-key>"

npx tsx scripts/backup/restore.ts --dir "C:\Users\<username>\AureliaBackups\<TIMESTAMP>"
```

### Remapping Database Image URLs to Target Project:
Because recipe image URLs store the full Supabase domain (e.g. `https://upzkcqovqstfsizerulx.supabase.co/storage/v1/object/public/...`), restoring to a new project requires updating the domain so images load from the new bucket:

1. Open `data/remap-storage-urls.sql` in the backup archive.
2. Replace `<NEW_PROJECT_REF>` with your new Supabase project ref (e.g. `target-dr-ref`).
3. Run the script in the target Supabase SQL Editor.
4. It updates:
   - `public.recipes.image_url`
   - `public.collections.cover_image_url`
   - `public.recipe_versions.snapshot` (JSONB)

### Public Image Accessibility Check:
Test accessing any restored image in your browser:
`https://<new-ref>.supabase.co/storage/v1/object/public/recipe-images/<user_id>/<file_name>`  
Confirm the image renders with HTTP 200.

## 9. Backup Archive Protection & Decryption

To safeguard user data in transit or off-site:
1. **Encrypting Backup Archives**:
   ```powershell
   npx tsx scripts/backup/encrypt-backup.ts --password "YourStrongPassphrase"
   ```
   Generates an authenticated AES-256-GCM container (`<TIMESTAMP>.enc`).
2. **Decrypting Backup Archives**:
   ```powershell
   npx tsx scripts/backup/decrypt-backup.ts --file "C:\Users\<username>\AureliaBackups\<TIMESTAMP>.enc" --password "YourStrongPassphrase" --out "C:\RestoreFolder"
   ```
3. **Off-Site Storage (Zero Silent Costs)**:
   - Store encrypted `.enc` bundles on a BitLocker-encrypted external SSD or private cloud drive (Google Drive, OneDrive).
   - Never upload unencrypted backups or passwords to external services.
